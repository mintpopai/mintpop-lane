# 机场订阅与第一跳按订阅分配设计

日期：2026-09-28
状态：已与维护者逐段确认设计，待写实现计划
范围：服务端（apps/server）、管理端（apps/admin）、桌面端（mintpop-lane-desktop）

## 一、背景

当前第一跳（前置节点）按**节点**分配：导入订阅得到「分组」下的一批节点，管理员给用户点「自动分配」，`FrontNodeAllocator` 按故障域每域挑 3 个负载最低的节点写进 `user_front_node`，客户端据此生成两层 `fallback`。

这套模型有两个问题：

1. **机场是按订阅限速的，不是按节点。** 所购机场的订阅声明的带宽（如 300M）是该订阅所有连接共享的总带宽，节点本身的带宽远大于此。按节点分摊负载没有意义，真正要控制的是「一个订阅承担多少人」。
2. **绑到节点上，节点一变用户就断。** 机场换域名、增删节点、改名时，用户分配到的节点可能整组失效，而分配只在管理员点击时才执行。

新模型改为按**机场订阅**分配：每个用户得到一个有序的订阅列表（每家机场最多一个），订阅内部由 mihomo 的 `url-test` 自己挑最快的节点。节点变化只影响订阅内部，不影响用户与订阅的绑定。

## 二、已确认的决策

- 新增「机场」实体，管理端新增机场页，字段：名称、地址（官网或用户中心）、备注。
- 原「分组」改造为「机场订阅」，页面上叫「订阅」。新增三项属性：所属机场、购买账号、带宽（Mbps）。**带宽与所属机场创建后不可修改。**
- 每个用户分到一个**有序订阅列表**：第 0 位是主用，其后是备用；每家机场在列表里最多出现一次；长度最多 **M = 3**。
- **只有主用占容量**：每人按 **20 Mbps** 计，订阅主用容量 = `带宽 ÷ 20`（向下取整）。备用不占容量。
- 顺序按「场景负载」算法分配（见第四节），对任意多家机场都成立。
- 可用机场不足 M 家时，列表变短（冗余降级），不报错。
- 所有订阅主用名额都满时，分配报错。
- **只能由管理员手动分配**：用户详情页「自动分配」（整份重算）与「取消分配」（清空，需二次确认）。
- 外层（跨订阅）用 `fallback`，内层（订阅内）用 `url-test`，容差取大值，`interval` 比现在的 180 秒小。
- **不背历史包袱**：清掉旧分组、订阅导入的节点、手工建的前置节点、用户第一跳分配；删除 `user_front_node` 表、`app_user.front_node_id` 列与链路配置里的 `front` 字段。客户端强制更新，不做旧版兼容。
- 第一跳只能来自机场订阅，不再支持手工新建前置节点。
- 常量写死在代码里：每人 20 Mbps、每人最多 3 家机场。

## 四、分配算法

### 4.1 概念

- **用户列表** `order`：`[(机场, 订阅), …]`，按顺位排列，长度 ≤ M。
- **故障场景** F：一组「挂掉的机场」集合。
- 场景 F 下，每个用户会落到自己列表里**第一个机场不在 F 中**的那一项。
- **场景负载_F(S)**：场景 F 下最终落到订阅 S 上的用户数。
  - F = ∅ 时就是 S 的**主用人数**。
  - 只看「挂了哪些机场」这个集合，与这些机场在各用户列表里的先后无关；列表更短的用户（如 `[A, X]` 在 F = {A, B} 下）也会被正确计入。

### 4.2 场景负载的计算

一次遍历全部用户即可得出所有订阅在场景 F 下的负载：

```java
/** 场景 F（这些机场都挂了）下，所有用户最终落在各订阅上的人数 */
static Map<Long, Integer> scenarioLoad(Set<Long> failedAirports, List<FrontAssignment> assignments) {
    Map<Long, Integer> load = new HashMap<>();
    for (FrontAssignment a : assignments) {
        for (FrontSlot slot : a.slots()) {                 // 按顺位从前往后
            if (!failedAirports.contains(slot.airportId())) {
                load.merge(slot.subscriptionId(), 1, Integer::sum);
                break;                                     // 只落到第一个活着的
            }
        }
        // 列表里的机场全在 F 中：该用户在此场景下无处可去，不计入
    }
    return load;
}
```

它是纯函数，与数据库无关，单独单测。

### 4.3 给一个用户分配列表

```java
List<FrontSlot> allocate(List<FrontAssignment> others, List<CandidateSubscription> candidates) {
    List<FrontSlot> order = new ArrayList<>();
    Set<Long> failed = new HashSet<>();                    // 当前顺位的场景：前面已选的机场都挂了

    for (int i = 0; i < MAX_AIRPORTS_PER_USER; i++) {
        Map<Long, Integer> load = scenarioLoad(failed, others);
        final int position = i;
        CandidateSubscription best = candidates.stream()
                .filter(s -> !failed.contains(s.airportId()))
                // 第 0 位额外受主用容量限制：此时 failed 为空，load 就是主用人数
                .filter(s -> position > 0 || load.getOrDefault(s.id(), 0) < s.primaryCapacity())
                .min(Comparator
                        .comparingDouble((CandidateSubscription s) ->
                                (load.getOrDefault(s.id(), 0) + 1.0) / s.bandwidthMbps())
                        .thenComparing(CandidateSubscription::id))   // 平手按 id，结果确定可复现
                .orElse(null);

        if (best == null) {
            if (i == 0) {
                throw new BizException(BizCodeEnum.FRONT_CAPACITY_FULL); // 所有订阅主用名额都满了
            }
            break;   // 可用机场不足 M 家：列表变短，冗余降级
        }
        order.add(new FrontSlot(best.airportId(), best.id()));
        failed.add(best.airportId());                      // 下一顺位的场景：连这家也挂了
    }
    return order;
}
```

- `MAX_AIRPORTS_PER_USER = 3`，`BANDWIDTH_PER_USER_MBPS = 20`，主用容量 `primaryCapacity = bandwidthMbps / 20`。
- **候选订阅**：至少有一个「启用中且判定为美国」的节点（`UsLandingNodes.isUsLanding`）。没有可用节点的订阅不参与分配，避免把用户分到空订阅上。
- `others` 是**除本用户以外**全部用户的列表：重算已分配用户时，他自己的旧列表不能挡住自己。

### 4.4 例子

三家机场各一个 300M 订阅 A1、B1、C1（容量各 15），已有用户：

| 用户 | 列表 |
|---|---|
| u1 | A1, B1, C1 |
| u2 | A1, C1, B1 |
| u3 | B1, A1, C1 |
| u4 | C1, A1, B1 |

给 u5 分配：

- 第 0 位，F = ∅：主用负载 A1 = 2、B1 = 1、C1 = 1；加上 u5 后 A1 = 3/300、B1 = 2/300、C1 = 2/300，平手按 id 选 **B1**。
- 第 1 位，F = {B}：u1、u2、u3 落到 A1，u4 落到 C1；加上 u5 后 A1 = 4/300、C1 = 2/300，选 **C1**。
- 第 2 位，F = {B, C}：四人全落到 A1，只剩 A1 可选，选 **A1**。

结果 u5 = `[B1, C1, A1]`。

### 4.5 事务与并发

分配在一个事务内完成：

1. 锁住全部 `airport_subscription` 行（`SELECT … FOR UPDATE`），串行化并发的分配；
2. 读出候选订阅与除本用户外的全部列表；
3. 运行 4.3 的算法；
4. 删除本用户原列表，写入新列表。

计算量：M 个场景 × 用户数，千人规模毫秒级，不维护统计表，每次现算。

### 4.6 生命周期

- **只由管理员触发**：「自动分配」整份重算，「取消分配」清空。不在开通席位或拉取链路时自动分配。
- 已分配的用户不会被自动挪动；新增订阅只服务之后的分配。
- 订阅被用户引用时不能删除，提示先给这些用户重新分配。
- 机场下还有订阅时不能删除。

## 五、链路下发（服务端）

`LinkConfigResponse` 删除 `front` 字段，第一跳只由 `frontGroups` 承载。

`LinkServiceImpl` 构造 `frontGroups`：

1. 按顺位读取用户的 `user_front_subscription`；为空报 `EGRESS_NOT_ASSIGNED`。
2. 每个订阅生成一个 `FrontGroup`：节点取该订阅下**启用中的美国节点**，照旧套用保活参数覆盖（`FrontTuningProperties`）。
3. 节点为空的订阅跳过；全部为空报 `NODE_DISABLED`。
4. `frontGroups` 按顺位排列，客户端外层 `fallback` 即按「主用 → 备用 1 → 备用 2」兜底。
5. `FrontGroup.failureDomain` 仍作三期、四期上报的关联键：取该订阅节点中**出现次数最多**的故障域，平手取字典序最小，全未解析为 `null`。上报链路不改。

**已知限制**：`link_report` 的唯一键是 `(user_id, failure_domain, window_start)`，同一用户的两个订阅若取到同一个 `failureDomain`（两家机场共用中转、或都未解析出故障域而同为 `null`），两组各自的上报会互相覆盖，链路健康数据失真。当前用法下每人最多三家机场各一个订阅，一般不会撞上；下一期由客户端按故障域合并上报窗口，或服务端保证同一用户的分配列表内故障域唯一。

## 六、桌面端（mintpop-lane-desktop）

`render.rs` 的组参数：

| | 现在 | 改为 |
|---|---|---|
| 内层（每个订阅一组） | `fallback`，`interval: 180` | `url-test`，`tolerance: 150`，`interval: 60`，`lazy: false` |
| 外层（跨订阅） | `fallback`，`interval: 180` | `fallback`，`interval: 60` |

- 内层关闭 `lazy`：备用订阅平时不被使用，开着 `lazy` 不会测速，外层可能拿过时节点误判其不可用。
- 健康检查地址仍为 `<服务端>/api/ping`。
- 内核中的组名、节点名（`us-front-<i>`、`us-front-<i>-<n>`）不变，采样与上报代码不改。
- 删除 `LinkConfigData.front` / `LinkConfig.front`，以及 `render.rs` 中「没有可用分组时退回单个 front」的旧分支；`frontGroups` 全空时视为链路不可用。

**真内核实测结论（2026-09-28）**：mihomo v1.19.14（桌面端随包的 `mihomo-aarch64-apple-darwin`），本机回环起 socks5 充当节点、HTTP 204 充当 `/api/ping`，经控制接口 `/group/<组>/delay` 主动触发测速，断言落在 `/proxies` 的 `now` 与 `/connections` 上。测试见桌面端 `src-tauri/tests/two_layer_fallback.rs`（需 `MIHOMO_BIN`）。

1. **外层 `fallback` 检查内层 `url-test` 组时，走的是该组当前选中的节点——成立。** 主用内层 = [死节点, 活节点]、备用内层 = [活节点]：内层测出活节点后，外层这一轮检查死节点被拨 0 次、活节点被拨 1 次，外层 `now` 保持主用。**例外在加载瞬间**：内外层首轮检查同时开跑，外层经主用拨号时内层还没有任何测速结果，只能选列表第一个，且这个选择被缓存 10 秒，于是外层首轮把主用判为不可用、选了备用（本机 11/11 次如此），要等外层下一轮检查（60 秒）才回到主用（**前提是有流量时**：外层 `lazy` 默认开启，没有流量时不会主动测速，滞后可能更久）。对用户：刚建链时若主用订阅列表第一个节点恰好不通，头一分钟会走备用订阅，流量不断，只是没走主用。
   - 顺带实测：`url-test` 的选中结果缓存 10 秒，定时检查测完后不清缓存，所以节点挂掉后内层最多滞后约 10 秒才换节点（**源码确认**，非跑表实测出的上限）。
2. **`url-test` 切换节点时，已建立的连接不会断——成立。** 经内层建一条到回显服务的长连接后，让当前节点不再接新连接并触发测速，内层切到另一个节点；切换后老连接仍能收发（`/connections` 里它的 `chains` 仍是旧节点），新连接走新节点。
3. **`tolerance: 150` 防抖——部分成立，与设计假设有出入。** 两个节点 40ms / 90ms 且每轮交换谁快（差 50ms），连续 5 轮测速：当前节点是组内第二个及以后的成员时，`now` 5 轮不变，tolerance 生效；**当前节点是组内第一个成员时，mihomo 不套用 tolerance**（`fast()` 判断「当前节点是否仍在组内」只从第二个成员查起，把第一个成员当成已不存在），只要别的节点快一点就切走，之后停在新节点上不再来回跳；对照组 `tolerance: 0` 每轮都切。对用户：每个订阅开头那个节点最多多换一次节点（一次新握手），不会出现持续来回切换。`INNER_TOLERANCE_MS` 保持 150。切回首成员后会再次失去防抖，同样的多切一次可能反复出现，但不会连续来回跳：从别的节点切回首成员时 tolerance 生效，首成员必须快出 150ms 以上才会被切回；切回之后，别的节点只要稍快就会再被切走。成因见第十二节 12.1 第五条（mihomo 的 bug）。
   - **现役订阅的实际延迟分布未测**：需要用真实账号登录桌面端、在用户网络下建链，本次没有做；150 是否大于同订阅节点间的正常延迟差仍待上线后观察。

**健康检查请求量**：每用户每 60 秒约 3 × 12 + 3 次，约 0.65 次/秒，全部打到 `/api/ping`；500 用户约 325 次/秒。作为上线后观察指标。

**已知限制**：`failovers` 指标的含义已经变化，且跨订阅切换目前不上报。采样仍把内层组 `now` 的变化记为一次 failover，但内层改为 `url-test` 后，这也会把「有更快节点出现」的择优切换计入（含上面实测三提到的首成员多切一次），不再单纯是「原节点不可用才切换」；真正的跨订阅切换发生在外层 `us-front`，目前没有采集，`failovers` 反映不出主用/备用之间的切换。

## 十一、测试

- **场景负载纯函数**：4.4 的例子；「挂掉机场集合相同、顺序不同」的用户计入同一场景；列表更短的用户落到后面机场被正确计入；列表机场全在 F 中的用户不计入。
- **分配算法**：主用满额报 `FRONT_CAPACITY_FULL`；可用机场少于 3 家时列表变短；重算时排除本用户旧列表；平手按订阅 id；同一机场不重复出现；无可用美国节点的订阅被跳过；带宽不同的订阅按比例填充。
- **并发**：两次分配同时进行，同一主用订阅不超容量。
- **链路下发**：按顺位排序；空订阅跳过；全部为空报 `NODE_DISABLED`；未分配报 `EGRESS_NOT_ASSIGNED`；`failureDomain` 取值规则；响应中不再有 `front`。
- **引用保护**：订阅被用户使用时不能删；机场下有订阅时不能删；订阅的机场与带宽不能改。
- **桌面端**：内层 `url-test` 带 `tolerance`、`interval`、`lazy: false`，外层 `fallback`；配置中没有 `front` 字段时正确解析；`frontGroups` 全空时视为不可用。
- **真内核实测**：第六节三点。
- **管理端**：机场页、导入弹窗新字段、订阅编辑只读项、用户详情两个按钮，真实浏览器检查。

### 12.1 第二期设计须知（2026-09-28 读 mihomo 源码确认）

以下结论来自 mihomo v1.19.14 源码（桌面端随包版本），**尚未在真内核上实测**；第二期实现热加载时须补一个真内核测试（写法照第六节实测二：建长连接 → 推送只改第一跳的新配置 → 断言老连接仍能收发、新连接走新配置，并测出暂停窗口时长）。

**一、整份配置热加载（`PUT /configs`）不会断开已建立的连接。** 依据 `hub/executor/executor.go` 的 `ApplyConfig`：

- 全流程没有关闭全部连接的调用。
- 出站节点替换（`tunnel.UpdateProxies`）只是整体换掉节点表，旧节点对象不关闭；已建连接持有旧节点的底层连接，用到自身结束为止。
- 入站监听器由 `listener.PatchInboundListeners` 处理：配置完全相同（本项目的 `agent-in` 在同一次运行内端口与凭据不变）则原样跳过；即使配置变了，`Listener.Close` 也只停止接受新连接，已接入的连接在各自协程里继续。

**二、热加载期间新到的连接会被直接拒绝。** `ApplyConfig` 开头 `tunnel.OnSuspend()`、结尾 `tunnel.OnRunning()`，其间 `handleTCPConn` 对新 TCP 连接直接 `Close`。窗口为一次热加载的耗时（预计毫秒级，待实测）；恰好落在窗口里的请求失败一次，Claude Code 会自动重试。可考虑只在用户空闲时热加载。

**三、每次热加载都会重演「首轮误判主用」。** 热加载会重建全部策略组，内层 `url-test` 的测速结果与外层 `fallback` 的状态全部清零，第六节实测一的问题（外层首轮只能经主用内层的第一个节点探测、结果缓存 10 秒，第一个节点不通时误判主用不可用、先走备用约一分钟）会在每次热加载后重新出现。因此「心跳发现配置变化就热加载」必须与「主动测速」一起做：热加载后先对每个内层组调 `/group/us-front-<i>/delay`，再对外层调 `/group/us-front/delay`。

**四、第一跳节点切换本身不断连接。** `url-test` / `fallback` 只在新连接拨号时选节点，切换只影响之后的新连接（第六节实测二已实测）。

**五、`url-test` 的容差对组内第一个节点不生效，是 mihomo 的 bug。** `adapter/outboundgroup/urltest.go` 的 `fast()` 在找最快节点的循环里顺带检查「当前节点是否仍在组内」，但循环从 `proxies[1:]` 开始，第一个节点永远查不到，`fastNotExist` 恒为真，容差被绕过。最新版 v1.19.31 与 Meta、Alpha 分支仍未修复；上游已有 issue [MetaCubeX/mihomo#2945](https://github.com/MetaCubeX/mihomo/issues/2945)（2026-07-07 提出，至今无回复）。可选处理：等上游修复（改一行即可）、向上游提 PR（对外操作，需确认）、或在每个内层组首位放一个不会被选中的占位成员（需实测，且影响采样的节点编号）。当前影响仅为偶尔多切一次节点、多一次握手，暂不处理。
