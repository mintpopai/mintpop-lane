# Lane 登录体系重构 · 设计文档

- 日期：2026-08-19
- 状态：已评审，待实现
- 取代：`2026-08-16-lane-terminal-design.md` 中「身份与登录」「用户模型」相关章节（其余章节仍有效）
- 关联参照：`mintpop-shop` 的 BFF 登录实现（`SecurityConfig` / `OidcLoginSuccessHandler` / `SessionTokenService`）

## 1. 背景与问题

产品定位从「公司内部员工工具」转为**面向公众的付费产品**。现有登录体系是内部工具模型的直接产物，存在结构性问题：

1. **用户必须先由管理员在数据库/管理端手工建好**（含手抄 Logto 的 user id），否则登录成功也会得到 `ACCOUNT_NOT_ENROLLED`。面向公众产品不可接受。
2. **服务端不在登录环节**：桌面端与管理端网页都直连 Logto 做 PKCE，服务端只当资源服务器验 JWT。因此无法在首次登录时自动建档，也拿不到用户邮箱（id_token 被桌面端丢弃）。
3. **会话生命周期受制于 Logto**：客户端长期持有 Logto 的 refresh/access token，吊销只能靠心跳查库间接兜底。
4. **用户模型把三件事揉在一行**：身份（你是谁）、链路资源（给你哪条通道）、服务权益（你买了什么、到什么时候）全部塞在 `app_user`，Claude 凭据是用户表上的一列——多 agent（Claude / Codex …）一出现即破产。

## 2. 目标与非目标

### 目标

- 任何人可自助注册（Logto 邮箱注册）并登录，首次登录自动建档，管理员不再手工建用户。
- 服务端进入登录环节：Logto 只回答「你是谁」，会话凭据由本系统自签、自管、自吊销。
- 服务权益建模为**订阅（subscription）**：一次购买一条记录，按 agent 分开卖，一个用户可持有多条（含同 agent 多条），各有起止期与凭据。
- 桌面端与管理端网页**两端一起**切到服务端自签会话，服务端只维护一套鉴权。
- 桌面端会话流：选 agent → 选套餐 → 选 workspace → 在该目录运行对应 agent CLI 并注入所选订阅的凭据。

### 非目标（本次不做）

- 支付/订单/对账：收款发生在系统外，管理员线下确认后手工开通。
- 订阅到期后自动回收落地节点与凭据：管理端可见「已到期」，由管理员手工处理。
- 多席位在单会话内切换之外的高级 UI（按 tab 选席位已覆盖需求）。
- refresh token / 会话刷新：过期即重新走浏览器登录。
- claimed HTTPS 深链（Universal Links / App URI）：列为后续可选加固。

## 3. 架构总览

### 3.1 模式选择

采用与 `mintpop-shop` 同构的 **BFF 模式**：

| | 现状（废弃） | 新设计 |
|---|---|---|
| Logto 握手 | 桌面端/网页各自直连 Logto（PKCE） | 服务端作为机密客户端完成全部握手（`oauth2Login`） |
| API 凭据 | Logto access token（资源服务器验签） | 本系统自签 HS256 JWT |
| 建档 | 管理员手工建（手抄 sub） | 登录成功回调里 `syncOnLogin` 自动建档 |
| 邮箱 | 拿不到 | 服务端亲手换得 id_token，email 可信 |
| 吊销 | 心跳查库间接兜底 | 每请求查库，改一行库下一个请求即生效 |

### 3.2 Logto 侧

- 现有「原生应用」（桌面）与「SPA」（管理端）两个应用**退役**；API Resource（`https://api.lane.mintpop.internal`）**退役**。
- 只保留**一个「传统 Web 应用」**，归 lane-server 持有：client_id + client_secret，回调地址 `https://<api 域名>/auth/callback`。
- scope 固定 `openid profile email`。
- ⚠️ Logto 的 id_token 用 **ES384** 签名，Spring Security 默认只认 RS256，必须显式配置 `OidcIdTokenDecoderFactory` 的算法（shop 已踩过此坑，实现照抄）。

### 3.3 服务端角色

从「纯资源服务器」变为「BFF + 业务 API」：

- 引入 `spring-boot-starter-oauth2-client`，**移除** `oauth2-resource-server` 及 Logto issuer/audience 配置；
- 日常鉴权只认自签 HS256 JWT（`SessionTokenService`，实现从 shop 平移），claims 仅 `sub=app_user.id` + iat/exp；
- 同一 token 两种载体：管理端网页用 HttpOnly Cookie（SameSite=Lax），桌面端用 `Authorization: Bearer`；
- 角色与处置态**每请求查库**（沿现状），因此停用/吊销即时生效，无需会话表与吐销名单。

## 4. 登录流程

### 4.1 端点

| 端点 | 鉴权 | 作用 |
|---|---|---|
| `GET /auth/desktop/start?code_challenge=..&state=..` | 匿名 | 桌面端登录入口：challenge+state 写入短时握手 Cookie，302 到 `/oauth2/authorization/logto` |
| `/auth/callback` | 框架 | Spring `oauth2Login` 回调，成功进 `OidcLoginSuccessHandler` |
| `POST /api/auth/desktop/exchange` | 匿名 | 入参 `{ticket, verifier}`，校验后签发桌面端 Bearer token |
| `GET /auth/logout` | 会话 | 管理端登出（清 Cookie）。桌面端登出＝删钥匙串，无需端点 |
| `GET /api/me` | 会话 | 当前用户信息 + 订阅列表（桌面端启动验活与状态页） |

### 4.2 成功回调的分叉（一个 handler 服务两端）

1. `syncOnLogin(sub, email, name)`：库里无此 sub 即插一行（仅身份，无资源无订阅）；有则刷新 email/name。name 取 Logto 的 name，缺失用邮箱 @ 前缀兜底。
2. 请求携带桌面握手 Cookie → 生成 32 字节随机 **ticket**（内存表存哈希 + challenge + userId，**60 秒过期、一次性**；单实例部署内存表足够，重启只影响正在登录的人），302 到 `lane://callback?ticket=..&state=..`。
3. 无握手 Cookie → 管理端网页：签会话 token 写 HttpOnly Cookie，302 回管理端首页。

### 4.3 桌面端时序

```
生成 verifier + state（复用 pkce.rs）
→ 系统浏览器打开 {服务端}/auth/desktop/start?code_challenge&state
→ 用户在 Logto 完成登录（注册也在这里发生）
→ 深链 lane://callback?ticket&state 回桌面端，校验 state
→ POST /api/auth/desktop/exchange {ticket, verifier}
→ 获得 Bearer token 存 OS 钥匙串
→ 此后启动直接装载钥匙串 token，调 /api/me 验活；401 才要求重登
```

### 4.4 ticket 的安全论证

威胁：`lane://` 自定义 scheme 在桌面系统上不独占，恶意应用可抢注截取深链（RFC 8252 点名问题）。

防御（与现状对 Logto 的 PKCE 结构一比一平移）：

- **PKCE**：verifier 从未离开桌面端进程内存；窃得 ticket 无 verifier 兑换必失败；
- **一次性 + 短时效**：60 秒过期，兑换即销毁；同票二次兑换失败并记日志（有人抢票的信号）；
- **state 校验**：桌面端只认本次登录发起的回调，防「塞给你攻击者账号的 ticket」的反向攻击；
- ticket 为高熵随机串，不编码信息，服务端存哈希。

### 4.5 会话 token

- HS256 自签 JWT，密钥 ≥32 字节，与加密密钥同级管理（生产走 `.env` 注入）；
- **网页 Cookie TTL 7 天，桌面 Bearer TTL 30 天**；过期重新走浏览器登录，不做 refresh；
- 换签名密钥＝全员下线（应急手段）。

### 4.6 鉴权链改造

- `DbRoleJwtAuthenticationConverter` 退役，新建 `SessionAuthFilter`：Bearer 头或 Cookie 取 token → 验签得 userId → 查库取角色与处置态 → 装配 `GrantedAuthority`；
- `SecurityConfig`：删 `oauth2ResourceServer` 段；放行 `/auth/**`、`POST /api/auth/desktop/exchange`、`GET /actuator/health`；`/api/admin/**` 仍要 `ROLE_ADMIN`；`anyRequest().denyAll()` 保留；
- 管理端 Cookie 为 SameSite=Lax：**部署约束——管理端与 API 必须同注册域名**（如 `admin.x.com` + `api.x.com`），写入部署文档。

## 5. 数据模型

项目未发版、无历史包袱：**直接改写 `V1__init_schema.sql`**，开发库删除重建，不做增量迁移。

### 5.1 `app_user`（身份 + 链路绑定 + 处置态）

- 新增 `email VARCHAR(255) NOT NULL`（Logto 邮箱注册保证必有；仅展示与联系，不做唯一键，身份唯一键仍是 `subject`）；
- `name` 保持 NOT NULL（`syncOnLogin` 兜底填充）；
- `front_node_id` 改**可空**（注册时无任何资源），外键保留；
- **删除** `claude_credential_cipher`（凭据随订阅走）；
- `status` 语义收窄为**账号处置态**：`ACTIVE`（默认，注册即 ACTIVE）/ `SUSPENDED` / `REVOKED`。「能不能用服务」不由它表达，由订阅查询得出；
- `uk_app_user_subject`、`uk_app_user_land_node` 原样保留。

### 5.2 `subscription`（服务开通记录，新表）

```sql
id                BIGINT PK AUTO_INCREMENT
user_id           BIGINT NOT NULL      -- FK → app_user，ON DELETE CASCADE（删用户连订阅一起清）
agent_type        VARCHAR(16) NOT NULL -- 枚举 AgentType：CLAUDE / CODEX（可扩）
name              VARCHAR(64) NOT NULL -- 用户可见的套餐名，管理员填（如「Claude Max 席位 1」）
starts_at         DATETIME NOT NULL    -- 服务起期
ends_at           DATETIME NOT NULL    -- 服务止期
credential_cipher TEXT NULL            -- 该 agent 的席位凭据密文（AES-GCM，复用 CredentialCipher）
remark            VARCHAR(255) NULL
created_at / updated_at
-- 无 UNIQUE(user_id, agent_type)：一次购买一条记录，同 agent 可并行多条（多席位）或衔接多段（续费）
```

- 「在期」判定：`starts_at <= now < ends_at`，**纯查询、无定时任务**——判定点就在拉链路与心跳里，天然 fail-closed；
- 续费＝插入新记录（购买历史天然保留）；管理员也可直接延长某条的 `ends_at`；
- 全表中文注释，风格照 V1 现状。

## 6. 链路业务

### 6.1 `resolveLink` 新判定链（顺序即优先级，全部 fail-closed）

1. sub 查无此人（登录后被删）→ 按吊销处理；`status` 为 SUSPENDED/REVOKED → `LINK_REVOKED`；
2. 该用户订阅**一条都没有** → `SERVICE_NOT_PURCHASED`（客户端渲染购买引导）；**有但无一在期** → `SERVICE_EXPIRED`（渲染续费提示）；
3. `front_node_id` 或 `land_node_id` 为空 → `EGRESS_NOT_ASSIGNED`（文案改「链路资源尚未分配，请联系管理员」）；
4. 节点状态、出口 IP 校验不变；
5. 在期订阅逐条取凭据：**全都没配** → `CREDENTIAL_NOT_ASSIGNED`；部分有 → 只下发有凭据的（无凭据的 agent 单独不可用，不拖累链路）。

### 6.2 下发协议

`LinkConfigResponse` 的 `claudeCredential: String` 改为：

```
agentCredentials: [ { subscriptionId, name, agentType, credential, endsAt } ]
```

- `endsAt` 供客户端展示到期日；
- 客户端收到**不认识的 agentType 一律忽略**（服务端加新 agent 不逼客户端升级）。

### 6.3 心跳

返回值从复用 `UserStatus` 改为专门的 **`LinkStatus`**（Rust 端镜像同名枚举）：

- `ACTIVE`：正常；
- `SUSPENDED` / `REVOKED`：断链并回登录页；
- `EXPIRED`：人正常但在期订阅归零（使用中跨过止期）→ **断链但保留登录态**，提示续费；续费后无需重登，重连即可。

### 6.4 业务码增删

- 删：`ACCOUNT_NOT_ENROLLED`（登录即建档，此态不复存在）、`USER_ALREADY_EXISTS`（管理端不再建用户）；
- 增：`TICKET_INVALID`（21 段）、`SERVICE_NOT_PURCHASED`、`SERVICE_EXPIRED`（31 段）、`SUBSCRIPTION_NOT_FOUND`（41 段）。

## 7. 桌面端

### 7.1 退役清单（整块删除）

- `auth/oidc.rs`：直连 Logto 的授权 URL 构造、code 交换、refresh；
- `auth/bootstrap.rs` 及 `/api/client-config` 消费逻辑：引导配置拉取、三态、并发引导锁（服务端的 `ClientConfigController` / `ClientProperties` / `ClientConfigResponse` 一并退役）；
- 钥匙串条目从 `logto-refresh-token` 更名为本系统会话 token 条目。

桌面端唯一需要预知的配置只剩**服务端地址**（编译期注入，已有机制不动）。`pkce.rs` 保留复用（对象从 Logto 换成自家服务端）。

### 7.2 新建会话向导（三步）

```
选 agent（CLAUDE / CODEX，只列有在期订阅的）
→ 选套餐（该 agent 的在期订阅：name + 止期；仅一条则跳过此步）
→ 选 workspace 目录（系统目录选择器，记住最近使用）
→ 在该目录 spawn 对应 agent CLI，注入所选订阅的凭据环境变量
  + 代理环境变量（现有 fail-closed 注入逻辑不动）
```

- **凭据注入是会话级**：注入哪份 token 由用户建会话时所选订阅决定；
- PTY 会话载体从「裸 shell」变为「在指定 cwd 直接运行 agent 命令」；
- agent 类型 → CLI 命令与凭据环境变量名的映射表在桌面端维护（CLAUDE → `claude` / `CLAUDE_CODE_OAUTH_TOKEN`；CODEX 的命令与变量名落地时按其 CLI 现状确定）。

### 7.3 状态页

- 展示各订阅（名称、agent、止期）；
- 三种不可用文案：未购买（购买引导）/ 已到期（续费提示）/ 已停用（联系管理员）。

## 8. 管理端

### 8.1 网页登录改造

- 删除 `@logto/browser` 依赖与 `auth/logto.ts`；登录按钮跳服务端 `/oauth2/authorization/logto`，回来即带会话 Cookie；
- HTTP 客户端从「带 Bearer」改为「带 Cookie（credentials: include）」，401 时跳服务端登录入口。

### 8.2 功能改版

- **「新建用户」入口删除**（建档只来自登录）；`UserSaveRequest` 移除 `subject`；
- 用户列表：email / 姓名 / 处置态 / 链路资源 / 在期订阅摘要，可筛选「有无在期订阅」；
- 用户编辑收窄为：处置态 + front/land 节点分配；
- 用户详情新增**订阅管理**：列表 + 新增（agent、套餐名、起止期、凭据）/ 修改（延期、换凭据、改名）/ 删除；凭据留空沿用原值的既有逻辑照旧；
- 用户删除保留（清垃圾注册，级联删订阅）。

## 9. 测试策略

**服务端**（复用 MysqlTestBase）：

- exchange 端点：verifier 错误 / ticket 过期 / 重放，三个失败分支 + 成功分支；
- 成功回调建档：首登插入、再登刷新、幂等；
- `SessionAuthFilter`：验签、过期、Bearer 与 Cookie 两种载体、查库装配角色；
- `resolveLink`：§6.1 判定链逐分支；
- 订阅 CRUD 与管理端鉴权。

**桌面端**（Rust 单测）：state 校验、ticket 交换错误分支、多订阅下按所选订阅注入凭据。

**管理端**（Vitest）：401 重登路径、运行时配置简化后的行为。

**手工验收主链**：注册 → 管理员开通（分配节点 + 建订阅）→ 桌面端建会话跑 agent → 管理员把止期改到昨天 → 心跳断链并提示续费。

## 10. 配置与部署清单

- **Logto 控制台**：新建「传统 Web 应用」（回调 `https://<api 域>/auth/callback`）；删除原「原生应用」「SPA」与 API Resource；
- **服务端配置**：删 `spring.security.oauth2.resourceserver.*`；新增 Logto client 注册（client-id/secret）、会话签名密钥、管理端前端地址；生产密钥走 `deploy/.env`；
- **桌面端**：编译期注入仅剩服务端地址；
- **部署约束**：管理端与 API 同注册域名（SameSite=Lax 前提），写入部署文档。

## 11. 已知取舍

- **无 refresh token**：桌面端 30 天重登一次浏览器，换来省掉整套刷新轮换逻辑；
- **ticket 表在内存**：单实例部署下重启只影响正在登录的人；
- **到期不自动回收资源**：落地节点稀缺，但自动回收需定时任务与宽限期策略，等有真实到期用户再做；
- **每请求查库**：现状即如此（原本就按 sub 查角色），无新增成本，换来吊销即时生效；
- **Lax Cookie 的 GET 登出骚扰**：与 shop 同款取舍，无数据风险，接受。
