## 1. 背景与目标

桌面端登录 Logto 需要四个接入值，现在全部由构建期环境变量注入（`build.rs` 声明 + `lib.rs` 的 `option_env!` 读取）：

| 变量 | 含义 |
|---|---|
| `LANE_LOGTO_ISSUER` | Logto 租户的 OIDC issuer |
| `LANE_LOGTO_CLIENT_ID` | Logto 原生应用的 App ID |
| `LANE_API_RESOURCE` | 服务端在 Logto 注册的 API Resource 标识 |
| `LANE_SERVER_URL` | 服务端地址 |

这个形态有两个实际问题：

1. **换 Logto 租户或应用要重新出包、全员重装**。三个值里没有一个是秘密（公共客户端的 `client_id` 本来就会出现在浏览器地址栏），却被绑死在二进制里。
2. **一致性靠人肉核对**。客户端的 `LANE_API_RESOURCE` 必须与服务端 `spring.security.oauth2.resourceserver.jwt.audiences[0]` 逐字相同，否则 access token 的 `aud` 对不上，登录能过但每个接口都 401；两者分处两个仓库位置，配错时报错也不指向真正的原因。

本期把前三个值改为**由服务端在客户端启动时下发**，客户端只保留 `LANE_SERVER_URL` 一个编译期常量。

**成功标准**：换 Logto 租户 / 应用只需改服务端配置并重启，已装的桌面端下次启动即生效，无需重新出包；客户端拿到的 `resource` 与服务端校验的 `aud` 由同一份配置派生，不存在配不一致的可能。

## 2. 范围

### 本期做

- 服务端新增匿名端点 `GET /api/client-config`，下发三个 Logto 接入值
- 桌面端启动时拉取该配置并持有，登录流程改从内存配置取值
- 桌面端构建期注入变量从四个减到一个（`LANE_SERVER_URL`）
- 应用标识统一为 `ai.mintpop.lane`（`tauri.conf.json` 的 `identifier` 与钥匙串 service 名）
- CI 与文档同步

### 本期不做

- **配置端点承载其它引导信息**（最低客户端版本、服务公告等）。接口是加字段兼容的，真需要时再加，现在加只是徒增未使用的代码路径。
- **配置本地缓存**。拉不到就明确报错，理由见第 7 节。
- **测试版 / 正式版双应用标识**。所谓测试版就是本地源码编译产物，靠 `LANE_SERVER_URL` 的缺省值区分即可，见第 6 节。
- **`LANE_SERVER_URL` 的运行时化**。它是整条信任链的锚点，必须硬编码，见第 9 节。

## 3. 接口契约

```
GET /api/client-config        匿名，无需 Authorization
```

```json
{
  "code": 0,
  "data": {
    "logtoIssuer":   "https://<租户>.logto.app/oidc",
    "logtoClientId": "<Logto 原生应用的 App ID>",
    "apiResource":   "https://api.lane.mintpop.internal"
  },
  "msg": null
}
```

- 返回体沿用统一的 `ApiResponse<T>`，`code=0` 为成功。
- `logtoIssuer` **带 `/oidc` 后缀**：客户端按 `{issuer}/auth`、`{issuer}/token` 拼接授权与令牌端点（见 `auth/oidc.rs`）。
- 路径与 `/api/link/config` 的分工要一眼可辨：**client-config 回答「怎么登录」，link-config 回答「登录后给你什么」**。前者匿名，后者必须带 JWT。
- `redirect_uri` 不在下发范围内：它由客户端注册的 deep link scheme 决定（`lane://callback`），服务端说了不算。

## 4. 服务端设计

### 4.1 配置来源

三个值中只有 `logtoClientId` 是新配置，另外两个复用鉴权配置，从而让一致性由结构保证而非人工核对：

| 下发字段 | 来源 |
|---|---|
| `logtoIssuer` | `spring.security.oauth2.resourceserver.jwt.issuer-uri` |
| `apiResource` | `spring.security.oauth2.resourceserver.jwt.audiences[0]` |
| `logtoClientId` | 新增 `lane.client.logto-client-id` |

前两项通过注入 Spring Boot 自带的 `OAuth2ResourceServerProperties` 读取，不重复声明。

### 4.2 新增与改动

- `config/ClientProperties.java`：`@ConfigurationProperties("lane.client")`，字段 `logtoClientId`。
- `response/ClientConfigResponse.java`：record，字段 `logtoIssuer` / `logtoClientId` / `apiResource`，与 `LinkConfigResponse` 同风格。
- `controller/ClientConfigController.java`：`@GetMapping("/api/client-config")`，构造器注入 `ClientProperties` 与 `OAuth2ResourceServerProperties`，返回 `ApiResponse.success(...)`。
- `config/SecurityConfig.java`：在 `/api/**` 的 `authenticated()` **之前**插入

  ```java
  .requestMatchers(HttpMethod.GET, "/api/client-config").permitAll()
  ```

  顺序错了会被通配规则吃掉（与既有 `/api/admin/**` 必须排在前面同理）。
- `application-local.yaml.example` / `application-prod.yaml.example`：补 `lane.client.logto-client-id` 及中文注释。

不新增 `BizCodeEnum` 条目：配置缺失属于部署错误，不是业务错误。

## 5. 桌面端设计

### 5.1 配置获取与持有

新增 `auth/bootstrap.rs`：

```rust
pub async fn fetch_client_config(server_url: &str) -> Result<OidcConfig, RemoteError>
```

- 复用 `link::remote::ApiResponse<T>` 解析统一返回体，复用 `no_proxy()` 客户端——引导发生在链路建立之前，只能走用户自己的网络。
- 把下发的三个值与固定的 `redirect_uri: "lane://callback"` 组装成 `OidcConfig`。

`AppState` 新增 `oidc_config: Mutex<Option<OidcConfig>>`。

### 5.2 启动时序

```
setup
 └─ spawn bootstrap
      ├─ fetch_client_config 成功 → 写入 AppState
      │                            → emit auth://config-ready
      │                            → spawn try_silent_login
      └─ 失败 → emit auth://config-failed { reason }
```

现在 `try_silent_login` 在 `setup` 里直接 spawn，本期改为**串在引导成功之后**——它需要配置才能刷新令牌。

### 5.3 命令层改动

- `start_login` 保持同步 command，从 `AppState` 读配置；为空时返回「无法连接服务端，请稍后重试」，替换现在的「登录配置缺失，请联系管理员」（后者描述的是已经不存在的失败原因）。
- 新增 `reload_client_config` command：重跑引导，供登录页的重试按钮调用。
- `handle_callback` 与 `try_silent_login` 内的 `oidc_config()` 调用改为从 `AppState` 读取。
- 删除 `lib.rs` 中 `oidc_config()` 对三个 Logto 变量的 `injected!` 读取；`server_base_url()` 保留不变。
- `build.rs` 的 `INJECTED_KEYS` 只剩 `LANE_SERVER_URL`。

### 5.4 前端

`Login.vue` 增加「服务端不可达」状态：显示失败原因与重试按钮，按钮调 `reload_client_config`；成功后回到正常登录态。

## 6. 应用标识与本地自测

### 6.1 应用 id 统一为 `ai.mintpop.lane`

两处必须同时改，否则钥匙串条目名与应用标识漂移：

- `apps/desktop/src-tauri/tauri.conf.json` 的 `identifier`
- `apps/desktop/src-tauri/src/auth/storage.rs` 的 `const SERVICE`

副作用（均可接受，项目尚未正式分发）：macOS 视其为全新应用，旧的 `ai.mintpop.lane` 若装过需手动删除；钥匙串换 service 名后已存的 refresh_token 读不到，本机需重新登录一次。服务端 Java 包名 `ai.mintpop.lane` 与应用 id 无关，不动。

### 6.2 本地自测包与正式包的区分

不引入渠道机制。`server_base_url()` 在没有编译期注入时回退到 `http://127.0.0.1:8080`，区分天然成立：

| | 谁编译 | 传不传变量 | 连哪个服务端 |
|---|---|---|---|
| 本地自测包 | 开发者本机 `mise run build-desktop` / `run-desktop` | 不传 | `http://127.0.0.1:8080` |
| 正式包 | CI `release-desktop.yml` | 传 `vars.LANE_SERVER_URL` | 生产地址 |

这与 mise 规范「缺省指向最安全环境」一致。需要本地包连别的服务端时显式传一次即可。

**已知限制（不做机制，只在文档中知会）**：本地自测包与正式包的 `identifier` 与 `lane://` scheme 相同，同机共存时登录回调可能被另一个应用接走。自测期间应移除正式版。

## 7. 错误处理与降级

配置拉不到时**不做本地缓存回退**，直接失败并给出可操作的提示。理由：没有服务端就拿不到链路配置，即使登录成功也用不了；缓存只是把失败往后推一步，还会引入「旧 issuer 长期残留」这一类难查的问题。

| 场景 | 客户端表现 |
|---|---|
| 服务端不可达 / 超时 | 登录页显示「无法连接服务端」+ 重试按钮 |
| 返回 `code != 0` | 显示服务端 `msg` + 重试按钮 |
| 返回体字段缺失 | 显示「服务端配置异常，请联系管理员」 |
| 引导成功但静默登录失败 | 沿用现有行为：清掉本地 refresh_token，回到未登录态 |

## 8. 构建与发版

- `release-desktop.yml` 的构建步骤 env 只保留 `LANE_SERVER_URL`；仓库 Variables 中的 `LANE_LOGTO_ISSUER` / `LANE_LOGTO_CLIENT_ID` / `LANE_API_RESOURCE` 删除。
- **不兼容切换，发版顺序固定：先发服务端、再发桌面端**。新客户端要求 `/api/client-config` 已经上线，顺序反了会让新装的客户端直接卡在引导失败。这条写进 `deploy/README.md`。

## 9. 安全考量

- **`LANE_SERVER_URL` 是信任锚，必须硬编码进二进制**。客户端凭它决定「去哪儿要配置」；一旦可被本地文件或用户输入篡改，攻击者就能把 `issuer` 换成钓鱼页面骗取公司账号。生产环境该地址必须是 https。
- 下发的三个值均为公开信息，匿名端点不泄露任何秘密。真正的秘密（节点密码、Claude 席位凭据）仍只经 `/api/link/config` 下发且要求 JWT。
- 放行规则限定 `GET` 与精确路径，不使用通配，避免顺带放宽其它端点。

## 10. 测试策略

**服务端**（`ClientConfigControllerTest`，MockMvc）：

- 匿名请求返回 `code=0`，三个字段与配置一致
- `apiResource` 等于 `audiences[0]`，与鉴权配置同源
- 匿名请求 `/api/link/config` 仍返回 401，证明放行未波及其它路径

**桌面端**（`auth/bootstrap.rs` 单元测试，沿用现有不引 HTTP mock 的做法，只测纯解析）：

- `code=0` 的返回体正确映射为 `OidcConfig`
- `code != 0` 返回业务错误
- `data` 缺字段时报错而非静默用空串
- 组装出的 `redirect_uri` 恒为 `lane://callback`

## 11. 验收

1. 服务端配好 `lane.client.logto-client-id` 后启动，`curl` 匿名访问 `/api/client-config` 返回三个正确值。
2. 桌面端本地编译（不传任何变量）启动，能连本机服务端完成登录全流程。
3. 停掉服务端再启动桌面端，登录页显示「无法连接服务端」；启动服务端后点重试，恢复正常并可登录。
4. 在 Logto 侧换一个原生应用、改服务端配置重启，**不重新出包**，桌面端重启后用新应用完成登录。
5. 检查桌面端二进制中不再包含 Logto 租户地址（`strings` 搜不到 issuer 字符串）。
