# 时区处理设计：全链路 UTC 绝对时刻

日期：2026-08-20
状态：已与维护者确认设计，待实现

## 背景与问题

当前整条链路是**无时区墙钟**设计，靠「所有参与方在同一个时区」这个假设撑着：

- MySQL 列类型 `DATETIME`（无时区），JDBC URL 钉死 `serverTimezone=Asia/Shanghai`；
- 后端全链路 `java.time.LocalDateTime`，订阅在期判定用 `LocalDateTime.now()`（跟随容器 `TZ`）；
- compose 的 `TZ` 默认 `UTC`，README「建议」设为 Asia/Shanghai——与 JDBC URL 里钉死的时区存在不一致的可能；
- API 输出 `2026-08-18T10:20:30` 这类**不带偏移**的 ISO 串；
- admin 前端明确不做时区换算，裁字符串直接显示；desktop 端同样裁串取日期。

风险：管理员在美国经 admin 填订阅起止期，数字实际按服务端时区解释；换部署机或改 `TZ` 会让全部存量数据语义漂移；desktop 用户看到的到期时间无时区标注，全球用户各自理解各自的。

## 已确认的决策

1. **订阅起止期语义 = 绝对时刻**：到期是全球同一瞬间，不是某个时区的墙钟。
2. **尚未上生产、数据可丢**：不写存量数据换算迁移。
3. **直接修改 Flyway `V1__init_schema.sql`**（补 UTC 语义注释），本地开发库 drop 重建；不为注释新增 V2。

## 总原则

**存储、传输、计算一律 UTC；只在「人看的那一刻」换算成查看者本地时区。**

时区从此不再是配置项：`serverTimezone=Asia/Shanghai`、「订阅按服务端时区判定」这类钦定时区全部退场；`TZ` 降级为只影响容器日志时间戳。换部署机、换地区对业务零影响。

## 分层设计

### 1. 数据库（`apps/server/src/main/resources/db/migration/V1__init_schema.sql`）

- 列类型**保持 `DATETIME`**：不改 `TIMESTAMP`（避开 2038 上限与隐式会话时区换算），语义定死为 UTC。
- 所有时间列的 COMMENT 补「UTC 时间」字样（`created_at` / `updated_at` / `starts_at` / `ends_at`），直接改 V1。
- `ends_at` 的「止期不含」判定语义（`starts_at <= now < ends_at`）不变。

### 2. JDBC 连接（`apps/server/config/application.yml` 与 `application.example.yml`）

- URL 参数 `serverTimezone=Asia/Shanghai` 改为 `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`。
  - `connectionTimeZone=UTC`：驱动编解码时间值按 UTC；
  - `forceConnectionTimeZoneToSession=true`：把 MySQL **会话时区**也钉到 UTC，使 DDL 里 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` 由数据库自动填充的值同样是 UTC，与应用写入语义一致。

### 3. 后端（`apps/server`）

- **时间类型**：实体、DTO、request/response 中的 `LocalDateTime` 全部改为 **`Instant`**（订阅起止、`createdAt`/`updatedAt` 一视同仁）。涉及 `entity`/`dto`/`request`/`response` 各包下所有含时间字段的类。
- **持久层（MyBatis-Plus）**：MyBatis 内置的 `InstantTypeHandler` 经 `java.sql.Timestamp` 读写（保 epoch），配合 JDBC URL 的 `connectionTimeZone=UTC` 即按 UTC 编解码、与 JVM 时区脱钩，无需额外配置。`MybatisUserRepository` 里两处在期过滤 SQL 的 `NOW()` 改为 `UTC_TIMESTAMP()`——不依赖会话时区、意图自明。
- **时钟注入（DI）**：新增 `Clock` bean（`Clock.systemUTC()`），现有 4 处 `LocalDateTime.now()` 调用点（`AuthController`、`AdminUserServiceImpl`、`LinkServiceImpl` 两处）改为注入 `Clock` 后 `clock.instant()`；`SubscriptionDto.isActiveAt` 签名改为 `isActiveAt(Instant now)`。测试可注入 `Clock.fixed(...)`。
- **序列化**：Jackson 对 `Instant` 的默认 ISO-8601 输出即带 `Z`（如 `2026-08-18T02:20:30Z`），API 契约从「无时区串」升级为「带偏移串」，消费方无歧义；反序列化同理接受带 `Z` 串。

### 4. admin 前端（`apps/admin`）

- **展示**（`src/utils/format.ts` 的 `formatDateTime`）：语义反转——带 `Z` 的串**必须**交给 `Date` 解析（无歧义），按浏览器本地时区渲染 `YYYY-MM-DD HH:mm`；注释同步改写。所有展示处继续统一走 `formatDateTime`，不留散落的裁串逻辑。
- **表单输入**（`src/components/SubscriptionDrawer.vue`）：`el-date-picker` 按管理员浏览器本地时区取值，提交前转为 ISO UTC 串：去掉现有 `value-format="YYYY-MM-DDTHH:mm:ss"`，让 `el-date-picker` 绑定 `Date` 对象，提交时 `toISOString()` 得到 UTC 串；回填编辑时 `new Date(串)` 反向换算。
- **界面提示**：表单里现有「起止期按服务端时区解释，请与部署环境时区（compose 的 TZ）核对」的提示改为标注当前浏览器时区（如「按你的本地时区 UTC-7 填写」）。

### 5. desktop 端（`apps/desktop`）

- `App.vue` 与 `SessionWizard.vue` 的 `day()` 从裁串改为：解析带 `Z` 串，按用户本地时区取日期部分展示。中国用户看到的即北京时间日期，无需配置。

### 6. 部署与文档

- `docker-compose.yml`：`TZ` 注释改为「仅影响容器日志时间戳」；变量保留。
- `README.md`：删除「订阅起止期按服务端时区判定」的整段提示（首次部署第 3 步与可调参数表两处），`TZ` 行说明改为「仅影响日志时间显示」。

## 测试

- **在期判定**：`isActiveAt` 用 `Clock.fixed` 写边界用例——起含（`now == startsAt` 在期）、止不含（`now == endsAt` 不在期）。
- **API 契约**：Controller 测试断言 JSON 时间字段以 `Z` 结尾；写入接口接受带 `Z` 串并正确落库。
- **Repository/Fixtures**：现有测试中 `LocalDateTime` fixture 改 `Instant`，断言随类型同步；Testcontainers 的 MySQL 容器 URL 追加与生产一致的 `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`，并加一条「写入 Instant → 库内 DATETIME 字面值就是 UTC 墙钟」的落库断言（用 `DATE_FORMAT` 直查），防 JVM 时区渗入。
- **admin 前端**：`formatDateTime` 单测——给定 UTC 串 + mock 时区（如 `TZ=America/Los_Angeles` 跑 vitest 或用固定 offset 断言），验证本地时区渲染；表单提交换算的往返测试（本地填入 → UTC 串 → 回填一致）。

## 不做的事（YAGNI）

- 不做「按用户偏好时区显示」的设置项——浏览器/系统本地时区即正确答案。
- 不做存量数据换算迁移（无生产数据）。
- 不改 `TIMESTAMP` 列类型、不引入额外时间库（moment/dayjs 等），原生 `Date`/`Intl` 足够。
