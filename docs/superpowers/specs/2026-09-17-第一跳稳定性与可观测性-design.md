# 第一跳（前置节点）稳定性与可观测性

> 日期：2026-09-17 · 状态：已确认，待实施
> 涉及：`apps/server`、`apps/admin`（一、三期）；桌面端仓库 `mintpop-lane-desktop`（二、三期）

## 一、背景

lane 的链路是「客户端 → FRONT（机场节点）→ LAND（自有落地）→ 目标」。运行下来第二跳稳定、第一跳偶发不可用，且服务端对第一跳**没有任何观测手段**——`AdminNodeServiceImpl.probe()` 明确拒绝 FRONT 角色（`NODE_PROBE_UNSUPPORTED`），理由是服务端不带 mihomo 内核、连不上 trojan/anytls 这类协议。

动手之前先对现役机场订阅（TaiShan Net）做了一次链路测绘，结论推翻了「81 个节点 = 81 条链路」这个直觉：

- 订阅返回的是整份 Clash 配置（`RestClientSubFetchClient` 固定发 `clash.meta` UA），`proxies` 84 条，其中 3 条是伪装成节点的信息条目（剩余流量/重置/到期），真实节点 81 个，81 个互不相同的域名。
- **80 个 anytls 节点的域名全部 CNAME 到 `hk.tsdns.top`（57 个）或 `jp.tsdns.top`（23 个）**，靠**端口**区分后端落地机（端口连号按地区分段：HK `35355-35376`、SG `27521-27535`、US `35660-35677`…）。这是标准的「中转入口 + 端口分流」架构。
- `tsdns.top` 托管在阿里云云解析企业版（NS `vip7/vip8.alidns.com`），配了**分运营商线路解析**，TTL **30 秒**：

  | 入口域名 | 电信 | 联通 | 移动 | 境外 |
  |---|---|---|---|---|
  | `hk.tsdns.top` | `34.84.255.241`（GCP 东京） | `43.199.66.164`（AWS 香港） | 同左 | 同左 |
  | `jp.tsdns.top` | `13.192.233.178` / `13.196.205.245`（AWS 东京，轮询） | 同左 | 同左 | 同左 |

- 剩下 1 个 vless 节点 `[境外用户专用]GPT01` 独立直连（AS202662 Hytron 香港），不在中转体系内，**与本项目无关，不纳入**。
- **12 个美国节点全部落在 `jp.tsdns.top` 这一个故障域下。**

结论：**这个订阅对一个具体用户只提供 1 个第一跳入口**。节点数量不等于冗余度。

而 lane 的 LAND 节点做了**国家级 GeoIP 限制、只接受美国来源**，前置只能选落地在美国的那 12 个——可选故障域从 2 个进一步掉到 1 个。

第一跳单点 + 零重试（`app_user.front_node_id` 是单选，`LinkServiceImpl.resolveLink()` 直接下发这一个节点，客户端不会自己换路）= 入口一抖，用户就是硬故障。

## 二、诊断出的成因

按与「**偶发**」这一特征的吻合度排序。加粗的是本方案直接处理的。

| # | 成因 | 机制 | 用户感知 |
|---|---|---|---|
| ① | **anytls 空闲即断连接池** | 订阅未配会话参数，走 mihomo 默认值（官方文档：`idle-session-check-interval` 30s、`idle-session-timeout` 30s、`min-idle-session` 0）。Claude Code 是突发式流量，思考间隔常超 30 秒，于是**几乎每次请求都要重新做 TCP+TLS 握手**——而握手正是最容易被干扰的时刻 | 放一会儿回来第一下失败，重试就好 |
| ② | **入口 IP 被封后换机** | 30 秒 TTL 就是为「被封即换」准备的。封 → 该入口下全部节点同时挂 → 机场改 A 记录 → 几分钟后自愈 | 断几分钟，没管它自己好了 |
| ③ | **入口机拥塞 / QoS** | 一个入口 IP 承载几十个端口的全部用户流量。且指纹显眼：`sni: ''` 时 mihomo 回落用 `server` 做 SNI（官方文档确认），即**明文暴露真实域名**（不像 reality 伪装成 `www.cloudflare.com`），叠加单 IP 上几十个连号高位端口的长连接 | 晚高峰持续变慢但不断 |
| ④ | DNS 层 | 30 秒 TTL 意味着客户端高频解析；`.top` / `.icu` / `.app` 后缀在国内被污染概率偏高 | 随机解析失败 |
| ⑤ | 中转 → 落地的隧道抖动 | 机场内部链路（如东京中转 → 美国落地），对我们完全不可见 | 某节点忽好忽坏 |
| ⑥ | 并发设备数限制 | 机场普遍有，本订阅配额未知 | 随机断连 |
| ⑦ | **订阅流量耗尽** | 128 GB 额度（测绘时已用 33.68 GB），耗尽则该组节点同时全挂 | 突然全挂 |
| ⑧ | **配置过期** | 订阅刷新是管理端手动触发的，机场改端口/域名后库里就是旧值 | 某些节点永久不通 |
| ⑨ | **单点无重试** | `front_node_id` 单选，内核不会自己换路，上面任一瞬时抖动都直接变成用户可见的硬故障 | 放大以上全部 |

## 三、已确认的决策

1. **LAND 的美国限制是国家级 GeoIP，不是 IP 白名单。** 任何美国出口都可用，机场换落地 IP 与本项目无关——**不做白名单维护，不做自动加白**。
2. **前置节点只能选「落地在美国」的节点**，这是 LAND 决定的硬约束，不放开。注意约束的是第一跳的**出口**（机场落地机的 IP），不是**入口**（客户端连的那台中转机，它永远是机场安排的、不可选）。
3. **采购两家机场。** 单机场内的入口冗余由机场决定、不可控，多机场是入口层冗余的唯一来源。
4. **冗余按「故障域」组织，而不是按机场或节点。** 故障域 = 域名解析链的终点（CNAME 末端；无 CNAME 则为节点域名本身）。两家机场完全可能租同一家中转服务商，按机场分组会骗过自己。
5. **不按 IP 分组。** 入口 IP 的 TTL 只有 30 秒、随时会变；CNAME 名字是稳定的。
6. **故障转移用两层嵌套 `fallback` 组**，不用 `url-test`、不用单层平铺（理由见 §5.2）。
7. **每个故障域取 K=3 个节点。** K 放配置，可按三期的上报数据再调。
8. **一期不做 anytls 会话参数的实测验证。** 按官方文档做保守调整并配置化；出问题清空配置即回退原状。
9. **可观测性只走客户端上报**，不做服务端拨测第一跳、不做境内探测点（理由见 §4）。

## 四、非目标

- **不做服务端直连探测第一跳。** 两个独立理由：(a) 服务端不引入 mihomo 内核是既有设计约束；(b) 即便引入，服务端在海外，与大陆用户解析到的入口**不是同一套**（实测：电信走 GCP 东京，其余走 AWS 香港），测出来的通断对大陆用户没有推断力。这是视角性失真，不是精度问题。
- **不自建境内探测点。** 一台机器只代表一个运营商，而入口恰恰是分运营商的；要覆盖得三台，成本与收益不匹配。真实用户天然分布在各运营商，是更好的探针。
- 不做 LAND 白名单相关的任何功能（决策 1）。
- 不改第二跳（LAND）——它现在是稳的，`EgressCheckService` 那套继续按原样跑。
- 不改支付、订单、席位凭据、官网。
- 不做机场的自动采购/比价；尽调只出数据，买不买由人定。
- 不做「一个用户跨机场同时建多条链路」这种主动多路；只做故障转移。

### 5.1 故障域是整个方案的地基

`proxy_node.failure_domain` 这一列贯穿三期：

- **一期**：采购尽调靠它判断「第二家是不是跟第一家同一个中转」。
- **二期**：分配算法靠它保证下发的节点真的跨入口。
- **三期**：上报聚合靠它——按节点聚合没有意义，同一故障域下的节点不是独立样本。

没有这一列，后两期都无从下手，所以它排在一期第一位。

### 5.2 为什么是两层 fallback

mihomo 的策略组可以嵌套（官方文档：「策略组通过 `proxies` 字段引入出站代理**或其它策略组**」）。我们诊断出的故障恰好是两层，结构一一对应：

| 层 | 组 | 救什么 | 不救什么 |
|---|---|---|---|
| 内层 | 每个故障域一个 `fallback` | 该入口背后某台**落地机**挂了（成因 ⑤，以及落地机被封/欠费/带宽满） | 入口机本身 |
| 外层 | 包含全部内层组的 `fallback` | **入口机**挂了（成因 ②③），整组不可用时切到另一家 | —— |

**为什么不能平铺成一个组**：平铺后 A 家入口一挂，fallback 要依次试完 A 家全部节点（它们在同一台机器上，会全部超时）才轮到 B 家，用户干等数十秒。分层后内层组整体不可用会立刻反映到外层，**一步切到 B**。

**为什么是 `fallback` 不是 `url-test`**：`url-test` 按延迟择优会频繁切换，每切一次就是一次新握手——与成因 ① 的治理方向（尽量复用热连接）正好相反。`fallback` 只在当前节点不可用时才换，保持粘性。

**健康检查目标用 lane 自己的 `/api/ping`**（返回 204），不用 `gstatic.com/generate_204`：少一个外部依赖，走自己的 Cloudflare 域名（符合 `global-reachability` 规范），且服务端顺带能看到探测流量。

## 六、一期：服务端地基（零客户端改造）

一期全部改动落在 `apps/server` + `apps/admin`，不动桌面端，可独立上线。

### 6.1 故障域解析 `FailureDomainResolver`

新增 `ai.mintpop.lane.client.FailureDomainResolver`（接口 + 实现，按 DI 规范由配置类装配，测试可替换）：

```
String resolve(String host)
```

- 对 `host` 做 A 查询，取**应答里 CNAME 链的末端名字**；无 CNAME 时返回 `host` 本身（该节点自成一个故障域）。
- 解析失败返回 `null`，调用方按「未知」处理，**不写入、不报错、下轮再试**（与 `EgressCheckService` 对探测失败的处理一致：网络抖动不等于事实变化）。
- 实现用 JDK 的 `InitialDirContext`（`dns:` provider）直接查 CNAME 记录，不依赖外部 HTTP。
- 结果**不缓存**：调用点只有「导入/刷新订阅」和「尽调」，频率低。

### 6.2 订阅尽调

**做成管理端接口，不做独立脚本**——解析逻辑要与导入流程共用一份 `FailureDomainResolver`，拆成脚本必然漂移；且 `scripts/` 下目前只有 `release.sh`，为此引入新工具链不值得。

`POST /api/admin/node-groups/audit`，入参 `{ subUrl }`，**只读不落库**，返回：

| 字段 | 说明 |
|---|---|
| `airportName` | 取自 `content-disposition` 的 `filename*` |
| `totalNodes` / `usNodes` | 节点总数 / 判定为美国落地的节点数 |
| `failureDomains` | `[{ domain, nodeCount, usNodeCount, entryIps, asns }]` |
| `conflictsWith` | 与库中已有节点撞故障域的分组名列表——**非空即否决** |
| `protocols` | 出现过的 `type` 集合，用于确认 §6.3 的覆盖表是否已支持 |
| `traffic` | `{ usedBytes, totalBytes, expiresAt }`（来自 §6.4 的响应头） |
| `lineSplit` | 四运营商视角解析是否返回不同 IP（有分线路者国内优化更好） |

「美国落地」的判定：节点名匹配 `US|美|United States` 或含 🇺🇸。**这是启发式**，机场命名不规范时会误判——尽调报告里把判定出的节点名一并列出让人核对，不做自动化决策（见 §11 取舍）。

`entryIps` / `asns` / `lineSplit` 需要按运营商视角解析，用 `dns.google/resolve` 的 `edns_client_subnet` 参数（四个代表性子网写死在配置里）；ASN 反查复用已有的 `IpTimezoneClient` 同源服务 `ipwho.is`。

管理端在「节点分组」页加一个「尽调」入口：粘贴链接 → 看报告 → 决定是否走现有的导入流程。

### 6.3 前置参数覆盖表

治理成因 ①。**关键在 `min-idle-session: 1`**：即使机场服务端自己 30 秒就掐会话，客户端也会在后台主动补一条——握手依然发生，但**发生在后台而非用户请求的关键路径上**。这条对机场服务端的行为不做任何假设，所以不会白做。

在 `ProxyNodeDto.toMihomoNode()` 里，按 `sourceType`（真实 mihomo type）查覆盖表并合并进下发参数：

```yaml
lane:
  front-tuning:
    anytls:
      idle-session-check-interval: 30
      idle-session-timeout: 300     # 默认 30s → 5min
      min-idle-session: 1           # 默认 0 → 1，维持一条热连接
```

- 表里没有的协议**原样透传，不做任何覆盖**——加机场不用改代码。
- 整段配置为空即完全恢复现状，这是回退手段。
- 只覆盖 FRONT；LAND 不走这条路径。
- 用户自己在订阅里已显式配了同名键时，**以覆盖表为准**（覆盖表是我们的调优结论，机场的默认值不是）。

> ⚠️ 数值未经实测（决策 8）。拉长空闲超时理论上可能触发机场的异常长连接限速。上线后若出现「连接建立后很快被掐」的新症状，先把 `idle-session-timeout` 调回 30 再排查。

### 6.4 订阅元信息与额度告警

治理成因 ⑦。`SubFetchClient.fetch()` 现在只返回 body，把响应头整个丢了。改签名：

```java
record SubFetchResult(String body, Long usedBytes, Long totalBytes, Instant expiresAt) {}
SubFetchResult fetch(String subUrl);
```

- 解析 `subscription-userinfo: upload=…; download=…; total=…; expire=…`（`used = upload + download`，`expire` 是 epoch 秒）。
- 头缺失或格式不认识 → 三个字段为 `null`，**不影响导入**（不是所有机场都返回这个头）。
- 落到 `node_group` 新增列，每次拉取（导入/刷新/尽调）都更新。
- 用量 ≥ 80% 或剩余不足 3 天 → 推飞书，复用 `NodeNotifyService` / `FeishuBotClient`。**同一分组同一档位只推一次**（库里记 `traffic_alerted_at` + 档位，跨档或重置后才再推），避免每轮刷新都刷屏。
- 管理端分组列表展示用量进度条与重置日期。

### 6.5 订阅定时刷新

治理成因 ⑧。新增 `SubRefreshService`，`@Scheduled(fixedDelayString = ...)`，默认 24h（对齐机场返回的 `profile-update-interval`）：

- 逐个分组重新拉订阅，复用 `AdminNodeGroupServiceImpl` 已有的刷新逻辑（按「同组内 `source_name` 相同」匹配同一节点）。
- 同时更新 §6.4 的额度字段与 §6.1 的 `failure_domain`。
- **只更新已存在的节点，不自动新增、不自动删除**——订阅里新冒出来的节点是否启用是运营决策，自动拉进来会绕过人的判断。发现增删只推飞书告知。
- **节点的端口/地址变了要推飞书**，因为这意味着之前下发给用户的配置已经失效。
- 任一分组失败只记日志，不中断整轮（与 `EgressCheckService.checkAll()` 同构）。

### 6.6 入口 IP 监控

服务端测不到「通不通」，但能测到「换没换」——**机场换入口 IP ≈ 刚被封过**，这是封锁事件的间接信号，且纯 DNS 查询就能拿到。

新增 `EntryIpWatchService`，`@Scheduled` 默认 5 分钟：

- 对库里全部 distinct `failure_domain`，按四个运营商视角（电信/联通/移动/境外）各解析一次。
- 与 `entry_ip_history` 里该 `(failure_domain, vantage)` 的最新一条比对，变了就插一条新记录并推飞书。
- 某个视角连续 N 轮解析失败 → 推飞书（可能是该运营商线路被掐）。
- 解析失败不写入、不清空历史。

### 6.7 数据模型 `V20__front_stability.sql`

```sql
    id             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    failure_domain VARCHAR(255) NOT NULL COMMENT '故障域（中转入口域名）',
    vantage        VARCHAR(16)  NOT NULL COMMENT '解析视角：CHINA_TELECOM / CHINA_UNICOM / CHINA_MOBILE / OVERSEAS',
    entry_ips      VARCHAR(255) NOT NULL COMMENT '该视角解析到的入口 IP，多个以逗号分隔并按字典序排列',
    asns           VARCHAR(255) NULL COMMENT '入口 IP 对应的 ASN，顺序与 entry_ips 一致；反查失败为 NULL',
    observed_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '观测时间（UTC）',
    PRIMARY KEY (id),
    KEY idx_entry_ip_history_domain_vantage (failure_domain, vantage, observed_at)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4 COMMENT = '中转入口 IP 变更历史：IP 一变说明机场刚换机，是封锁事件的间接信号';
```

`vantage` 按 `enum-naming.md` 用 SCREAMING_SNAKE_CASE，成员名与字符串取值逐字一致。

### 6.9 业务错误码

**不新增错误码。** 尽调复用现有的 `SUB_FETCH_FAILED(410011)` 与 `SUB_PARSE_FAILED(410012)`——它内部就是「拉取 + 解析」，失败原因与导入完全同构，再造一个 `SUB_AUDIT_FAILED` 只是同义重复。

尽调里「与现有分组撞故障域」**不是错误**，它是正常返回的一项结论，页面据此展示。这与 `AdminNodeServiceImpl.probe()` 的处理一致：探测不通是检测要给出的答案，不是请求本身出错。

## 七、二期：两家机场 + 两层 fallback

### 7.1 数据模型 `V21__user_front_group.sql`

```sql
CREATE TABLE user_front_node
(
    id         BIGINT   NOT NULL AUTO_INCREMENT COMMENT '主键',
    user_id    BIGINT   NOT NULL COMMENT '用户 id，引用 app_user',
    node_id    BIGINT   NOT NULL COMMENT '前置节点 id，引用 proxy_node',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（UTC）',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_front_node (user_id, node_id),
    CONSTRAINT fk_user_front_node_user FOREIGN KEY (user_id) REFERENCES app_user (id),
    CONSTRAINT fk_user_front_node_node FOREIGN KEY (node_id) REFERENCES proxy_node (id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4 COMMENT = '用户可用的前置节点集合：按故障域分散下发，供客户端组 fallback 组';
```

`app_user.front_node_id` **保留**，语义收窄为「主前置节点」= fallback 组的首选，同时是老客户端唯一能理解的那一个。迁移脚本把现有 `front_node_id` 回填进 `user_front_node`。

### 7.2 分配算法

`AdminUserService` 分配前置时：

1. 候选集 = `role=FRONT` 且 `status=ENABLED` 且**判定为美国落地**的节点。
2. 按 `failure_domain` 分桶，**`failure_domain` 为 NULL 的节点不参与**（未解析成功的不能保证跨入口）。
3. 每桶取 K 个（`lane.front.nodes-per-domain`，默认 3），桶内取法用「已分配用户数最少优先」摊平负载。
4. 只剩一个桶时照常分配，但**管理端要显式提示「当前只有 1 个故障域，入口无冗余」**——这是采购信号，不能让它静默。
5. `front_node_id` 取第一个桶的第一个节点。

### 7.3 下发契约

`LinkConfigResponse` 新增字段，`front` 保留不动（老客户端照常工作）：

```java
/** 按故障域分组的前置节点。客户端据此组两层 fallback；老客户端忽略本字段、只用 front */
List<FrontGroup> frontGroups

record FrontGroup(
    /** 故障域标识，仅作组名与分组依据，不含敏感信息 */
    String failureDomain,
    /** 该故障域下的候选前置节点，逐个是完整 mihomo 节点定义 */
    List<Map<String, Object>> nodes
) {}
```

`resolveLink()` 里原来那句「节点查不到按内部错误处理」的逻辑保持：**组内有节点被禁用就跳过它，整组空了就丢掉这组，全空才报 `EGRESS_NOT_ASSIGNED`**。

### 7.4 桌面端组装

按 `frontGroups` 生成：

- 每个 `FrontGroup` 一个内层 `fallback` 组，组名取 `us-front-<序号>`。
  **`failureDomain` 只作为接口上的分组键与三期上报的关联键，不要拿它当 mihomo 组名**——生成的配置文件用户可见、可导出，组名里带着 `jp.tsdns.top` 等于把机场的中转拓扑直接摊开给用户看。序号与 `frontGroups` 的下标一一对应，三期上报时客户端仍回传 `failureDomain` 原值，服务端能对上。
- 一个外层 `fallback` 组 `us-front`，`proxies` 按序引用各内层组。
- `land` 节点的 `dialer-proxy` 指向 `us-front`。
- 两层的健康检查都用 `https://<lane 域名>/api/ping`，`interval: 180`，`max-failed-times` 取小值让切换更快。
- `frontGroups` 缺失或为空 → 回退到旧的单 `front` 逻辑（兼容服务端未升级的情况）。

服务端新增 `GET /api/ping` 返回 204，**不需要鉴权**（它是健康检查目标，客户端此时还没建好链路）。

## 八、三期：可观测性

### 8.1 上报契约

**复用已有的 `POST /api/link/heartbeat`，不新开端点**——它已经在周期性跑了，省一个端点也省一次往返。请求体从空改为可选的上报块（老客户端不带 body，服务端照常返回心跳结果）：

```json
{
  "groupId": 3,
  "failureDomain": "jp.tsdns.top",
  "resolvedEntryIp": "34.84.255.241",
  "window": { "ok": 47, "handshakeFailed": 3, "timeout": 1, "dnsFailed": 0 },
  "p50LatencyMs": 180,
  "failovers": 2
}
```

- **`resolvedEntryIp` 是整个方案里最有价值的字段**：客户端实际解析到的入口 IP，服务端永远算不出来（分运营商解析）。有了它才第一次看得见真实拓扑。
- 窗口按客户端心跳周期聚合，**不逐请求上报**。
- 状态跃变（通→不通、不通→通、每次故障转移）不等窗口，立即触发一次心跳。
- **运营商由服务端按请求来源 IP 反查 ASN**，不让客户端自报（自报不可信，且客户端也不知道）。

### 8.2 数据模型 `V22__link_report.sql`

`link_report` 表按 `(user_id, group_id, failure_domain, window_start)` 存窗口聚合，附 `resolved_entry_ip`、`source_asn`、`isp`。保留期：原始窗口 7 天，按天聚合 90 天（用定时任务归档）。

### 8.3 告警与展示

飞书（复用 `NodeNotifyService`）：

| 告警 | 触发 | 对应成因 |
|---|---|---|
| 入口 IP 变更 | §6.6 | ② 被封换机 |
| 故障域成功率跌破阈值 | §8.1 聚合 | ②③ |
| **单运营商成功率异常** | 按 ASN 分组 | 分线路故障 |
| 额度 ≥80% / 即将到期 | §6.4 | ⑦ |
| 订阅节点增删或端口变更 | §6.5 | ⑧ |

管理端新增「链路健康」页：**故障域 × 运营商**的成功率矩阵 + 入口 IP 变更时间线。**不按节点展示**——同一故障域下的节点不是独立样本，按节点看会误导。

## 九、第二家机场采购标准

用 §6.2 的尽调报告逐条卡：

| 检查项 | 门槛 |
|---|---|
| **美国节点的 `failure_domain`** | **与现有机场不得相同——撞了直接否决，一票** |
| 入口 ASN | ≠ AS16509（现有是 AWS 东京）。同在 AWS 相关性过高，降级处理 |
| 美国节点数 | ≥ 5 |
| 分运营商解析 | 有分线路者优先（国内优化更好） |
| 协议 | 记下来，§6.3 覆盖表需要为它补一条 |
| 流量额度 / 重置周期 / 价格 | 算每 GB 成本 |

第一条是硬门槛：**两家机场 CNAME 到同一家中转服务商，等于花两份钱买一个故障域**，而这在机场圈很常见、不主动查发现不了。

## 十、测试

- `FailureDomainResolver`：有 CNAME 链 / 无 CNAME / 多级 CNAME / 解析失败，四种情况。DNS 查询抽成接口，测试用假实现。
- 参数覆盖表：表里有该协议 / 没有该协议 / 整段配置为空 / 订阅自带同名键（以覆盖表为准），四种。
- `subscription-userinfo` 解析：正常 / 缺头 / 格式不认识 / 数值溢出。
- 额度告警去重：跨 80 档推一次、再轮不推、跨 95 档再推、重置回落后清档。
- 分配算法：一个故障域 / 两个故障域 / 某桶节点不足 K / 全部节点 `failure_domain` 为 NULL。
- 下发契约：新老客户端各一份断言，确认 `front` 字段行为未变。
- 定时任务：单个分组失败不中断整轮（与 `EgressCheckService` 同构的测试写法）。

## 十一、已知取舍

1. **「美国落地」靠节点名启发式判定**（匹配 `US|美|United States|🇺🇸`）。机场命名不规范会误判，尽调与分配时都把判定结果列出来让人核对，不做纯自动决策。要精确只能实连探测每个节点看出口 IP，而服务端没有内核——做不到。
2. **`failure_domain` 是快照**。机场可以随时改 CNAME 结构，靠 §6.5 的 24h 刷新对齐；这期间下发的分组可能已经不跨入口了。接受这个窗口。
3. **一期的会话参数未经实测**（决策 8），数值是按官方文档的保守调整，配置化便于回退。
4. **两层 fallback 增加客户端健康检查开销**：K=3、两个故障域 = 6 个节点 + 3 个组在跑检查。`interval: 180` 下量很小，但 K 调大要重新评估。
5. **成因 ④⑥（DNS 污染、并发设备限制）本方案不直接治理**，只在三期变得可见。前者要靠客户端 DNS 策略，后者要问机场配额。
6. **上报数据带用户维度**，属于使用行为数据。保留期已限定（7 天 / 90 天），不外发。
7. **`/api/ping` 不鉴权**，会被任意人探测。它只返回 204、不含任何信息，可接受；但要确认它不进访问日志的高频写入路径。
