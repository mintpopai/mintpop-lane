# 第一跳可观测性（三期）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让第一跳的真实健康状况第一次变得可见——客户端主动采样每个前置节点的通断与延迟，按窗口聚合后随心跳上报；服务端按「故障域 × 运营商」还原真实拓扑并在成功率跌破阈值时告警。

**Architecture:** 桌面端每 30 秒对本用户的每个前置节点调一次 mihomo 的 `/proxies/{name}/delay` 触发采样（绕开 `lazy`），从 `/proxies` 读回 `alive` 与 `history`；每 5 分钟（第 5 次心跳）把窗口聚合结果塞进 `POST /api/link/heartbeat` 的请求体。服务端把来源 IP 反查成 ASN/ISP 后落 `link_report`，定时任务做「7 天原始窗口 → 90 天按天聚合」的归档，成功率跌破阈值且样本量足够时推飞书。管理端新增「链路健康」页展示故障域 × 运营商矩阵。**跨两个仓库。**

**Tech Stack:** 服务端 Spring Boot 3 / MyBatis-Plus / Flyway / MySQL 8.4 / Testcontainers；管理端 Vue 3 + TS + Vitest；桌面端 Tauri 2 / Rust / reqwest / tokio。

**Spec:** `docs/superpowers/specs/2026-09-17-第一跳稳定性与可观测性-design.md`（三期见 §8，**§8.0 是地基，动手前必读**；已知取舍见 §11 第 8、9 条）

## Global Constraints

以下数值与规则对所有任务生效，**取值逐字照抄，不要另起一套**：

- **采样周期 30 秒**；**上报窗口 5 分钟**（= 5 个心跳周期，心跳本身仍是 60 秒不变）。每节点每窗口 10 个样本。
- **成功率告警阈值 `< 0.80`**；**最小样本量 `samples >= 20`**，样本不足**一律不告警**（不是按 0/0 当 0% 报）。
- 三个数（采样周期、告警阈值、最小样本量）**全部可配置**，配置项在 `application.example.yml`，默认值即上述值。**它们未经生产实测**，与 spec §11 第 3 条同样的理由：配置化是为了能回退。
- **健康判据只能是 `alive`**。`history` 为空 → 计入 `noSample`，**不计入 `samples` 分母**；`delay == 0` 是合法的低延迟，**不是失败**（spec §8.0 两个陷阱）。
- 数据库表名、列名一律小写 snake_case，**每张表与每个字段都要写中文 COMMENT**。
- 业务错误码 6 位、接着 `41xxxx` 段现有的最大值往下走；统一 `ApiResponse<T>`，`code=0` 为成功。
- 枚举成员名与对外字符串取值一律 SCREAMING_SNAKE_CASE 且逐字一致。
- 注释、文档、提交信息用中文；标识符（含测试方法名）用英文，中文描述放 `@DisplayName` / `it()` 描述串。
- 后端分层 + 构造器注入；取「现在」一律走注入的 `Clock`，不直接 `Instant.now()`。
- **老客户端必须照常工作**：心跳请求体是可选的，不带 body 的请求返回值与现在逐字一致。

- Produces: 表 `link_report`、`link_report_daily`

**一个必须先想清楚的坑——唯一键里不能放可空列。**

MySQL 的 UNIQUE 索引对 `NULL` **不做唯一性判断**：多行 `NULL` 全部允许共存。所以若把 `failure_domain` 写成可空列再放进唯一键，**重复上报根本去不了重**——客户端重试一次就多一行，成功率分母被凭空放大。

本表的处理（**与二期契约层「`failureDomain` 可以是 null」不冲突，是同一语义在存储层的编码**）：

- `failure_domain VARCHAR(255) NOT NULL DEFAULT ''`，**空串 = 尚未解析出故障域**（不是「没有故障域」）。
- 接口层（`LinkHeartbeatRequest`、`LinkHealthResponse`）**保持 `null` 语义**，转换只发生在 Service 落库/读取的那一处，并在两侧各有一条测试钉住。

**本表刻意不存分组 id。** 写计划时的自查发现：客户端**根本拿不到**它——二期下发的 `FrontGroup` 只有 `{ failureDomain, nodes }`，没有 `node_group` 的主键。客户端手上唯一像 id 的东西是渲染时的**组下标**（0、1、2……），那是本地数组位置、与服务端主键毫无关系。若把它填进 `groupId`，两边都是数字、都能通过测试，语义却完全错位——与二期那个 Critical 同一个形状（契约冻结时看了形状没看语义）。而且三期的分析维度是「故障域 × 运营商」（spec §8.3 明确「不按节点展示」），分组根本不是维度；真需要时服务端可以从 `failure_domain → proxy_node → group_id` 反查。

```java
@PostMapping("/heartbeat")
public ApiResponse<HeartbeatResponse> heartbeat(
        @AuthenticationPrincipal Long userId,
        @RequestBody(required = false) @Valid LinkHeartbeatRequest report,
        HttpServletRequest httpRequest) {
    HeartbeatResponse response = linkService.heartbeat(userId);
    // 上报失败绝不能影响心跳本身：心跳承载的是"还能不能用"，
    // 观测数据丢一个窗口无所谓，把心跳搞挂会让客户端误判成链路失效
    if (report != null) {
        linkReportService.ingest(userId, report, clientIpOf(httpRequest));
    }
    return ApiResponse.success(response);
}
```

`clientIpOf` 取 `X-Forwarded-For` 的**第一段**（服务端在反代之后），缺头时回落 `getRemoteAddr()`。

```rust
    // 解析失败必须是 null。空串在服务端会被存成"未解析"之外的另一种东西，两边语义就岔了
}
```

- [ ] **Step 2: 跑测试确认红** — Run: `mise run test`

- [ ] **Step 3: 实现**

`resolved_entry_ip` 解析的是**前置节点配置里的 `server` 地址**（那就是中转入口域名）。用系统解析器，**失败返回 `None`，绝不 panic、绝不阻塞心跳**。

- [ ] **Step 4: 状态跃变时不等窗口，立即触发一次心跳**

这是 spec §8.1 的明文要求，写计划时的自查发现原稿十个任务一条都没覆盖，补在这里。

三种跃变要立即上报，**不等第 5 次心跳**：① 某故障域从「有 alive 样本」变成「一个都没有」；② 反过来，从「全无」恢复到「有」；③ 发生一次故障转移（组的 `now` 变了）。

先写会红的测试：

```rust
#[test]
fn losing_all_alive_samples_triggers_immediate_report() {
    // 第 2 次采样后某故障域 alive 归零 —— 断言不等到第 5 次心跳就发出上报块
}

#[test]
fn recovering_triggers_immediate_report_too() {
    // 反方向同样要报。只报"坏了"不报"好了"，看板上会一直挂着一个已经恢复的故障
}

#[test]
fn failover_triggers_immediate_report() { }

#[test]
fn immediate_report_resets_the_window_so_data_is_not_counted_twice() {
    // 立即上报之后窗口要清空，否则这批样本会在第 5 次心跳时被再报一遍，
    // 成功率的分母被放大。这条守的是"跃变上报"与"周期上报"的边界
}
```

**跃变上报要有最小间隔**（建议 30 秒，即一个采样周期），否则链路在临界点反复抖动时会把心跳打成高频请求。
